来源与边界：哪些是源码行为，哪些是教学算法？
  • 已核实：config.json：40 个主层，3 个 DSpark Blocks，5 个 Draft 槽位，128-token 私有窗口。Transformer.forward 在第 37/38/39 层执行前取输入，mHC 维取均值后拼接；forward_embed 执行 main_proj + main_norm，初始化 [anchor, noise×4] 并共享 Embedding；3 块后 mHC collapse + Norm + 共享 LM Head，得到 5 位置基础 Logits；Markov Head 根据前一 token 加偏置，再按顺序采样。Confidence Head 读取隐藏状态和 Markov embedding。
  • 当前 Decode 起点：本例从已有历史「我」和待输入「喜欢」的分块边界开始。40 层 Backbone 先处理当前输入，经 Final RMSNorm / LM Head 得到本轮 Logits，再选出 Anchor「先」；本轮 before 37/38/39 特征进入 DSpark。历史 forward_spec(start_pos=0) 仅播种私有窗口，返回 None；正 start_pos 的调用才生成候选。这个教学边界不表示 generate.py 默认将每个 Prompt 的最后 token 留出。
  • 公开生成脚本：inference/generate.py 的 generate 循环逐轮调用 model.forward(...)[0]，再写入一个 next_token；没有完整的 forward_spec → Verify → Accept/Reject 循环。Backbone 和 Draft 模块 forward 已实现，完整服务流程在此按概念展示。
  • CED：technical_report.txt §2.2 的优化 Prefill 包含 Encoder 全局 KV 投影和 Decoder SWA Bounded Replay；不能把 Decoder 操作全部删去。参考 forward 仍跑全部 40 层，没有该优化路径。Verification 使用同一 Target 架构，但处理 6 个新输入的位置；二者工作量不等同。
  • 标准算法：Greedy 的 Token ID 比较及概率接受、完整 residual 分布修正，依据 Speculative Decoding。调度依据报告 §2.4.3 与 DSpark 原论文；本仓库无完整 Scheduler / Verification / Accept-Reject runtime。参考 LM Head 默认只输出最后位置，验证 runtime 还须取得全部所需位置的 Logits。
  • 教学数据：A–E 和词块「我 / 喜欢」都是符号，不是真实 tokenizer 输出。所有向量都限定在图示 10-token 玩具词表，与真实 129280 维词表不同。概率模式 T=1，无 top-k / top-p，q 已包含 Markov 偏置；固定均匀数值用于重播采样，不使用随机数。Greedy 直接从 Target Logits 取 argmax，不对原始 Logits 做概率比值。各数据集改变 Target 分布，结果由算法计算。
