Roofline Analysis

The Roofline model estimates the upper bound of achievable performance for a computation, based on two hardware limits: how fast the accelerator can compute (peak compute throughput) and how fast it can move data between memory and compute (peak memory bandwidth). Comparing a workload's own Arithmetic Intensity against those two limits tells you which one is more likely to constrain it — this is a theoretical ceiling, not a measurement of real achieved performance.

Arithmetic Intensity

AI = FLOPs ÷ Memory Traffic

FLOPs: floating-point operations · Memory Traffic: Bytes · AI: FLOPs/Byte

Roofline Performance

Proof = min( Ppeak , AI × BWpeak )

Ppeak: FLOP/s (TFLOP/s) · BWpeak: Byte/s (GB/s or TB/s) · Proof: FLOP/s

Ridge Point

AIridge = Ppeak ÷ BWpeak

Units: FLOPs/Byte · Below the ridge: memory-bound. Above: compute-bound.

Proof is a theoretical bound, not measured hardware performance.

Worked Example: Query Low-Rank Projection

DeepSeek V4.1 Flash compresses its attention query through a low-rank bottleneck before expanding it back out to per-head queries. Parameters below are read directly from config.json: Hidden Size 5120, Q LoRA Rank 1280, Query Heads 64, Head Dimension 512 (Total Query Dimension 32,768).

X [M, 5120]
↓ WQA [5120, 1280]
H [M, 1280]
↓ RMSNorm — excluded from this baseline
↓ WQB [1280, 32768]
Q [M, 32768]

Scope: only the two linear projections (WQA, WQB) are counted below. RMSNorm and every other operation in the layer are excluded from this baseline — this is a scoped teaching example, not the full Attention module.

FLOPs (2MKN convention)

F = 2 × M × (5120 × 1280 + 1280 × 32768)

M is the number of tokens processed together in one batched matmul.

Memory Traffic (simplified BF16 HBM model)

Each weight and activation element is 2 Bytes (BF16). Weights are read once per batched computation; input, intermediate (written then read back), and output activations scale with M. This is a simplified logical traffic model, not a hardware trace — caching and kernel fusion are ignored unless stated.

Scenario A vs. Scenario B

Scenario A is not "1024 sequential single-token decode steps summed" — it is M = 1024 tokens genuinely processed together in one batched matmul (e.g. a prefill pass). The weight matrices are identical in both scenarios; only the activation traffic (and therefore the arithmetic intensity) changes with M.

Advanced (weight reuse & traffic assumptions)

This baseline always assumes weights are read exactly once per batched computation (ideal reuse across all M tokens in that one call) and that intermediate activations are written and read back once each. These assumptions are fixed for the worked example above; they are the same simplified HBM model described in the Memory Traffic section.

Model FLOPs Utilization (MFU)

MFU measures how much of a hardware setup's theoretical peak compute throughput is actually converted into useful model training throughput.

MFU

MFU = Model FLOPs/s ÷ Theoretical Peak FLOPs/s

Equivalently

MFU = (Fstep ÷ Tstep) ÷ ΣPpeak

Fstep: model FLOPs per training step · Tstep: step time (s)

FLOPstotal number of floating-point operations (a count)
FLOP/scomputational throughput (a rate)
TFLOP/s1012 FLOP/s
MFUdimensionless ratio, usually shown as a percentage

MFU is primarily a training efficiency metric. It is not: GPU/NPU utilization %, memory utilization, Hardware FLOPs Utilization (HFU, which counts recomputation too), or a Roofline arithmetic-intensity measurement.

Why "FLOPs per token" Isn't Simple for a MoE Model

A common dense-Transformer approximation is Training FLOPs/token ≈ 6 × Parameter Count. DeepSeek V4.1 Flash is a Mixture-of-Experts model, so total stored parameters and the parameters actually used by one token are very different — applying 6×total blindly overstates the real cost. (Attention computation, sparse position selection, shared operations, and sequence length also affect real training FLOPs; this section only corrects the MoE total-vs-active part.)

Both describe computational efficiency from different angles. Roofline alone cannot tell you MFU (it doesn't know your actual achieved throughput); MFU alone cannot tell you why a kernel is slow (it doesn't separate bandwidth- from compute-bound causes).
